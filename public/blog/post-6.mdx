# Какую базу данных выбрать для хранения и обработки данных с нуля


Данные, как вещи в доме, и чтобы не было бардака нам нужны разные системы хранения. В ИТ эти системы хранения - базы данных. Делюсь шпаргалкой для начинающих системных аналитиков и руководителей проектов для понимания какие сейчас актуальны базы данных и для каких задач.

**Актуальные тренды архитектуры данных 2025**

- **RAG и векторные индексы**\
  pgvector для Postgres, Pinecone/Weaviate/Qdrant

- **Локальная аналитика**\
  DuckDB для ноутбуков и мелких пайплайнов

- **Унификация lakehouse**\
  Iceberg/Delta/Apache Hudi на объектных хранилищах + движки (Spark, Trino, Dremio)

- **Распределённый SQL**

  CockroachDB/YugabyteDB для транзакций

- **Observability-стек**\
  Prometheus + VictoriaMetrics/ClickHouse + Grafana

- **Поиск + вектора**\
  Elasticsearch/OpenSearch с гибридным поиском (BM25 + dense vectors)

## Основные типы баз данных

### Реляционные базы данных (SQL)

 _Таблицы со строками и столбцами, связи между таблицами, строгие правила. Это швейцарский нож мира данных: надёжный, точный и универсальный для большинства задач, но не самый лучший для специальных условий._\
\- Когда выбрать именно реляционные базы данных: транзакции, деньги, заказы, учет, то есть, когда важна отчётность.\
\- Самые популярные реляционные базы данных: **PostgreSQL, MySQL, SQL Server**.\
\- Пример использования: интернет-магазины (таблицы с данными пользователей, заказов, товаров, платежей).


| **ПЛЮСЫ** | **МИНУСЫ** |
|:---|:---|
| ✅ **Надёжность (ACID)** — данные не потеряются: если операция началась, она выполнится до конца правильно, либо не выполнится совсем. Идеально для всего, что связано с деньгами и где нельзя допустить ошибку | ❌ **Масштабирование по горизонтали сложнее**, чем в других БД — трудно «размазать» одну базу на множество серверов, чтобы они работали как одно целое. Обычно ставят на один очень мощный сервер. Массовые запросы подвешивают систему |
| ✅ **Мощный SQL** — можно одним сложным запросом получить любую комбинацию данных из разных таблиц, отсортировать, подсчитать итоги и сгруппировать их | ❌ **Не гибкая!** — структуру таблиц и типы данных (что и как будет храниться) нужно продумать и задать заранее. Поменять потом — сложно и больно |
| ✅ **Нет дублирования данных!** | ❌ **Медленная на больших данных** — чем больше данных, тем медленнее работают сложные запросы с `JOIN` и агрегацией. Для больших объёмов данных и аналитики лучше использовать колоночные БД (например, ClickHouse) |


### Документные базы данных (NoSQL)

_Хранение объектов наподобие JSON (не одинарное значение, а много значений, как один элемент)._
\- Когда выбрать именно документные базы данных: разнородные данные, быстрая эволюция полей без миграций.\
\- Самые популярные документные базы данных: **MongoDB, Couchbase, Firebase Firestore**.\
\- Пример использования: каталоги товаров (где у каждого товара свои характеристики), профили пользователей, контент (статьи, блоги).


| **ПЛЮСЫ** | **МИНУСЫ** |
|:---|:---|
| ✅ **Гибкая структура** — можно хранить сложные объекты целиком, со всеми их внутренними свойствами, без необходимости дробить их на кучу таблиц | ❌ **Нет надёжных транзакций на несколько документов** — не подходит для систем, где критически важна точность и согласованность данных (банковские операции, бухгалтерия) |
| ✅ **Удобно для микросервисов** | ❌ **Дублирование данных** — одни и те же данные могут храниться в разных документах много раз, что влияет на размер хранилища и усложняет обновление данных |
| ✅ **Легко менять** — не нужно заранее придумывать строгую структуру таблиц и столбцов для всей базы. Структура может меняться для каждого документа | ❌ **Не подходят для аналитики!** (отчёты, подсчёт суммы, среднего и т.д.) |
| ✅ **Простая для начинающих разработчиков** — данные хранятся в форматах, которые легко понять (`JSON`, `XML`) | |


### Базы данных “ключ-значение”

_Хранение очень простой пары key → value._\
\- Когда выбрать именно базы данных ключ-значение: кэш, сессии, счётчики, pub/sub.\
\- Самые популярные базы данных ключ-решение: **Redis, Memcached, Aerospike, Riak**.\
\- Пример использования: идеально для кэширования (сохранения готовых данных на короткий срок), сессий пользователей на сайте, хранения настроек. 


| **ПЛЮСЫ** | **МИНУСЫ** |
|:---|:---|
| ✅ **Невероятно быстро выдаёт информацию** (миллисекунды) | ❌ **Очень тупые запросы** — может найти что-то только по точному ключу! |
| ✅ **Очень простой принцип работы** — всего несколько команд: положить / взять / удалить. Никаких сложных таблиц, связей и языков запросов. Низкий порог входа для разработчиков. Развернуть и начать использовать можно очень быстро | ❌ **Нет связей между данными** — нельзя создать отношения между разными ключами (например, пользователь → его заказы). Всю структуру данных нужно умещать в одном значении |
| ✅ **Легко масштабируется и отлично справляется с большими нагрузками** — можно просто добавить новые серверы, и данные распределятся между ними | ❌ **Ненадёжная** — часто данные в таких базах хранят ненадолго (кэш). Она не надёжна для хранения основной, критически важной информации (как, например, реляционная БД) |


### Базы данных с широкими столбцами (Wide-Column)

_Таблица с миллиардами колонок; строка хранится по ключу и колонкам-семействам._\
\- Когда выбрать именно базы данных Wide-Column: огромные объёмы, write-heavy, geo-распределённость.\
\- Самые популярные базы Wide-Column: **Cassandra, ScyllaDB, HBase**.\
\- Пример использования: аналитика сайта с большим количеством пользователей и действий (когда нужно хранить миллионы событий просмотров страниц в день и быстро получать статистику).


| **ПЛЮСЫ** | **МИНУСЫ** |
|:---|:---|
| ✅ **Обрабатывает огромные объёмы данных** — создана для работы с петабайтами информации, которые не поместятся на один сервер. Данные автоматически распределяются по множеству серверов (шардируются) | ❌ **Медленный SQL JOIN между таблицами** — плохо справляется с запросами, где нужно связать данные из разных таблиц или сделать простые вычисления (сумма, среднее и т.д.) |
| ✅ **Очень высокая скорость записи** — может записывать миллионы строк данных в секунду, это её главная суперсила | ❌ **Медленная согласованность** — данные на всех серверах обновляются не мгновенно. Если вы сразу после записи попробуете прочитать данные, скорее всего увидите старую версию |
| ✅ **Гибкая** — у каждой строки может быть свой набор столбцов (характеристик). Не надо заранее задавать одну структуру для всех записей | ❌ **Сложная настройка** — управлять сетью из сотни серверов намного сложнее, чем одним |
### Графовые базы данных
_Хранение сложных взаимосвязанных данных в виде узлов, связей и свойств (суперсила для анализа связей, но обычная задача для нее это как гонщику Фомулы-1 рулить фурой с картошкой)._\
\- Когда выбрать именно графовые базы данных: социальные связи, рекомендации, маршруты.\
\- Самые популярные графовые базы данных: **Neo4j, JanusGraph, TigerGraph**.\
\- Пример использования: аналитика паттернов в соцсетях, рекомендательных системах, обнаружении мошенничества и управления знаниями.


| **ПЛЮСЫ** | **МИНУСЫ** |
|:---|:---|
| ✅ Видит связи там, где другие базы слепые (если обычной БД нужно пройти по цепочке из нескольких таблиц как по лабиринту, то графовая сразу видит прямую связь) | ❌ Мало разработчиков, которые умеют с ней работать |
| ✅ Ищет связи между объектами мгновенно! | ❌ Не для простых задач! |
| ✅ Гибкая (не нужно заранее продумывать все возможные связи между людьми или объектами, а можно добавлять новые типы отношений на лету) | ❌ Ограниченная масштабируемость, большое потребление памяти (для больших объёмов данных нужно много ресурсов оперативной памяти, что дорого) |


### Векторные базы данных
_Хранение эмбеддингов (столбцы с сотнями/тысячами чисел)._- Когда выбрать именно векторные базы данных: поиск по смыслу, LLM-чаты, рекомендации контента.\
\- Самые популярные векторные базы данных: **Pinecone, Weaviate, Milvus, pgvector (Postgres)**.\
\- Пример использования: система поиска похожих товаров в интернет-магазине  **для AI/ML**.

| **ПЛЮСЫ** | **МИНУСЫ** |
|:---|:---|
| ✅ **Идеально для AI/ML** — ИИ преобразует любые данные (текст, картинку, звук) в вектор (цифровой отпечаток), а БД умеет быстро искать по этим отпечаткам | ❌ **Тупая БД ко всему, кроме векторов** |
| ✅ **Мгновенно находит самые похожие объекты** среди миллиардов других | ❌ **Дорогие ресурсы** — чтобы быстро искать, она должна хранить все векторы в оперативной памяти (RAM). А это очень дорого для больших объёмов данных |
| ✅ **Не ищет точные совпадения слов, а «понимает» смысл** и находит похожее | ❌ **Сложная настройка** (косинусное расстояние, HNSW, квантование) |


### Колоночные базы данных (OLAP)
_Данные хранятся по столбцам, оптимально для агрегаций._\
\- Когда выбрать именно колоночные базы данных: BI-отчёты, аналитика терабайтов.\
\- Самые популярные колоночные базы данных: **ClickHouse, BigQuery, Snowflake**.\
\- Пример использования: система аналитики для интернет-магазина, где нужно быстро генерировать ежедневные отчеты по миллионам заказов.


| **ПЛЮСЫ** | **МИНУСЫ** |
|:---|:---|
| ✅ **Высокая скорость аналитических запросов** — данные хранятся по столбцам, поэтому читаются только нужные колонки, а не целые строки | ❌ **Не подходит для OLTP и частых `UPDATE`/`INSERT` по одной записи!** |
| ✅ **Высокая компрессия и экономия хранения** — однородные значения внутри столбца хорошо сжимаются | ❌ **Сложная настройка пайплайнов данных** |
| ✅ **Встроенная оптимизация для аналитики** — индексы по сегментам/сайтовые статистики, векторизированное выполнение, пропуск сегментов, MPP/распределённая обработка | ❌ **Потенциальная задержка актуальности данных** — данные доступны с задержкой, что не подходит для real-time аналитики |


### Базы данных временных рядов (Time-Series)
_Оптимизация под метрику + timestamp._\
\- Когда выбрать именно эти базы данных: IoT, мониторинг, финансы.\
\- Самые популярные Time-Series базы данных: **InfluxDB, TimescaleDB, VictoriaMetrics*.\
\- Пример использования: система мониторинга температуры на производстве, где нужно каждую секунду собирать данные с 1000 датчиков температуры и быстро строить графики за любые периоды. 


| **ПЛЮСЫ** | **МИНУСЫ** |
|:---|:---|
| ✅ Временные ряды идеально сжимаются (сжатие 90+%) | ❌ Узкая специализация БД (простые операции типа точечного обновления значения по первичному ключу не поддерживаются) |
| ✅ Очень высокая скорость записи (массовая запись миллионов точек данных в секунду, что делает такие БД идеальными для IoT, телеметрии и мониторинга) | ❌ Сложные реляционные запросы с JOIN нескольких таблиц почти невозможно выполнить |
| ✅ Встроенные функции для работы со временем (запрос `SELECT avg(value) FROM metrics GROUP BY time(1h)` выполняется в тысячи раз быстрее, чем в реляционной БД) | ❌ Удаление больших объёмов данных — очень ресурсоёмко, что создаёт нагрузку |


### Базы данных Search / inverted index
_Токены → документы._\
\- Когда выбрать именно базы данных Search / inverted index: полнотекстовый поиск, лог-аналитика.\
\- Самые популярные базы Search / inverted index: **Elasticsearch, OpenSearch, Solr**.\
\- Пример использования: быстрый и умный поиск по 1 000 000 товаров с поддержкой в интернет-магазине.


| **ПЛЮСЫ** | **МИНУСЫ** |
|:---|:---|
| ✅ Поиск работает мгновенно, даже в огромной базе документов. Он умеет находить не только точные слова, но и их формы (например, бежать/бегу/бежит), понимает синонимы и исправляет опечатки. Обычные базы данных так не могут | ❌ Сложность обеспечения консистентности данных (ACID) (это не транзакционная БД!) |
| ✅ Мощный анализ и агрегация неструктурированных данных (агрегация, вычисление трендов по текстовым данным, анализ тональности, группировка результатов) | ❌ Высокие затраты на эксплуатацию + сложно настраивать (кластер из нескольких нод требует тонкой настройки, мониторинга и обслуживания, а переиндексация больших объёмов данных также требует ресурсов) |
| ✅ Высокая гибкость и масштабируемость (данные можно индексировать без строгого описания схемы + шардирование) | ❌ Не подходит для точечных запросов и сложных связей! |


### Базы данных Object Storage + SQL-движок (Lakehouse)
_Данные лежат в S3/MinIO, поверх них движок SQL (Iceberg, Delta, Hive)._\
\- Когда выбрать именно эти базы данных: легко масштабировать, дёшево хранить сырые данные + аналитика поверх.\
\- Самые популярные базы: **Databricks, Apache Spark + Iceberg**.\
\- Пример использования: глобальная аналитика городских транспортных потоков, оптимизация энергопотребления (данные с камер, датчиков освещения, систем общественного транспорта).


| Плюсы | Минусы |
|:---|:---|
| ✅ Очень низкая стоимость хранения | ❌ Сложная настройка (самостоятельное развёртывание и поддержка кластера Trino/Presto/Spark — это сложная инженерная задача. Managed-сервисы (AWS Athena, BigQuery) решают эту проблему, но стоят дороже за вычисления) |
| ✅ Максимальная гибкость (поддержка любых форматов данных, вы можете анализировать данные в их сыром виде (Parquet, JSON, CSV, Avro) без предзагрузки в СУБД. Это убирает этап ETL и позволяет data scientists и аналитикам самим работать с данными через единый SQL-интерфейс) | ❌ Для точечных запросов и OLTP-нагрузки не подходит! |
| ✅ Раздельное масштабирование (можно независимо масштабировать вычислительные мощности (добавляя ноды в кластер Trino/Presto/Spark) и хранилище (просто закидывая данные в S3). SQL-движки оптимизированы для быстрых аналитических запросов на больших объёмах) | ❌ Нет транзакционности и проблемы с ACID (S3 не поддерживает транзакции и атомарные перезаписи данных, что приводит к конфликтам при одновременной записи и чтении) |


### Встраиваемые базы данных Embedded / Edge
_Базы данных внутри приложения/устройства._\
\- Когда выбрать именно встраиваемые базы данных: мобильные, IoT-устройства без постоянного интернета.\
\- Самые популярные встраиваемые базы данных: **SQLite, DuckDB, Realm**.\
\- Пример использования: автономное управление теплицей (собирать данные с датчиков, управлять поливом и вентиляцией, даже если интернет пропал - и это все на маломощном устройстве (Raspberry Pi).


| Плюсы | Минусы |
|:---|:---|
| ✅ Полная автономность и независимость от сети (девайс работает полностью оффлайн) | ❌ Ограниченный объём данных и проблемы с масштабированием (хранилище ограничено объёмом диска edge-устройства (например, SD-картой на 32 ГБ)) |
| ✅ Мгновенная скорость отклика и низкая латентность (данные пишутся и читаются на локальном диске или даже в оперативной памяти (In-Memory), что очень важно, например, в роботостроении) | ❌ Сложность синхронизации данных (если данные всё же нужно передать в облако, то возникает очень сложная задача синхронизации) |
| ✅ Минимальные требования к ресурсам (БД потребляет минимум CPU, RAM и дискового пространства, что позволяет использовать их даже на телефоне с небольшим зарядом батареи) | ❌ Повышенные риски безопасности (в случае поломки устройства (сгорела плата, умер диск) данные теряются безвозвратно, если не была реализована синхронизация) |


## С чего начать: алгоритм выбора базы данных для проекта


## 1. Какие задачи будет решать проект?  

- [ ] Банковские операции, учёт (транзакции, деньги) → Реляционные (PostgreSQL, MySQL)

- [ ] Блог, контент-сайт → Реляционные (PostgreSQL, MySQL) или Документные (MongoDB, Couchbase)

- [ ] Социальная сеть (лента, профили) → Комбо: Реляционные (пользователи) + Документные (посты) + Графовые (Neo4j, JanusGraph) + Кэш (Redis)

- [ ] Аналитическая платформа, BI → Колоночные (ClickHouse, BigQuery) или Lakehouse (Databricks, Delta Lake)

- [ ] Мобильное/IoT-приложение → Встраиваемые (SQLite, Realm) + Бэкенд (PostgreSQL, MongoDB)

- [ ] Поисковый сервис, лог-анализ → Поисковые (Elasticsearch, OpenSearch, Meilisearch)  

- [ ] Система рекомендаций, ИИ-ассистент → Векторные (Qdrant, Weaviate, pgvector) + Графовые (Neo4j)  

## 2. Что за данные?

- [ ] Структурированные (таблицы, формы, заказы, пользователи) → Реляционные (PostgreSQL, MySQL, SQL Server)

- [ ] Полуструктурированные (XML, JSON, логи) → Документные (MongoDB, Couchbase) / Поисковые (Elasticsearch) / Реляционные (PostgreSQL с JSONB)

- [ ] Неструктурированные (файлы, изображения, видео) → Объектное хранилище (Amazon S3, MinIO) + Реляционные/Документные для метаданных

- [ ] Временные ряды (метрики, датчики) → Специализированные Time-Series (InfluxDB, TimescaleDB, VictoriaMetrics)

- [ ] Текст для поиска → Поисковые (Elasticsearch, OpenSearch, Meilisearch) / Векторные (Qdrant, Pinecone)

- [ ] Связи (сети, рекомендации) → Графовые (Neo4j, JanusGraph)

## 3. Какой объём?

- [ ] Гигабайты → Реляционные (PostgreSQL, MySQL) / Встраиваемые (SQLite для низкой нагрузки, DuckDB)

- [ ] Терабайты+ → Колоночные (ClickHouse, BigQuery) / Wide-Column (Cassandra, ScyllaDB) / Lakehouse (Spark + Delta Lake)

## 4. Какой режим работы?

- [ ] Частые записи, редкое чтение (логи, события) → Wide-Column (Cassandra, ScyllaDB) / Time-Series (InfluxDB, TimescaleDB)

- [ ] Частое чтение, редкие записи (справочники, каталоги) → Реляционные (PostgreSQL, MySQL) / Документные (MongoDB)

- [ ] Транзакции (деньги, заказы) → Реляционные с ACID (PostgreSQL) / NewSQL (CockroachDB, YugabyteDB) / MongoDB (с ограничениями)

## 5. Какая скорость доступа нужна?

- [ ] Макс. скорость, минимальная задержка (кэш) → Ключ-значение (Redis, Memcached) / CDN для статического контента

- [ ] Высокая скорость отклика (пользователь ждёт) → Реляционные / Документные с индексами (PostgreSQL, MongoDB)

- [ ] Приемлемая задержка (аналитика, отчёты) → Колоночные (ClickHouse) / Lakehouse (Databricks)

## 6. Нужен ли сложный поиск?

- [ ] По точным значениям → Реляционные (SQL WHERE в PostgreSQL, MySQL)

- [ ] По тексту (в т.ч. с ошибками, морфологией) → Поисковые (Elasticsearch, OpenSearch, Meilisearch для небольших объёмов)

- [ ] По смыслу (семантический) → Векторные (Qdrant, Pinecone, pgvector)

## 7. Как база справится с ростом данных?

- [ ] Вертикальное масштабирование (увеличение мощности сервера) → Реляционные (PostgreSQL, MySQL)

- [ ] Горизонтальное масштабирование (добавление серверов, шардинг) → NoSQL (MongoDB, Cassandra, ScyllaDB) / Распределённый SQL (CockroachDB, YugabyteDB)

- [ ] Геораспределённость → Распределённые базы (CockroachDB, YugabyteDB, DynamoDB)

## 8. Есть ли возможность использовать облачные сервисы?

- [ ] Локальные сервера → MySQL, PostgreSQL, MongoDB Community, Redis, ClickHouse

- [ ] Облако (Managed-сервисы) → Amazon RDS, Aurora, Google Cloud SQL, Azure Database, DynamoDB, BigQuery, Atlas (MongoDB)

## 9. Есть ли команда для поддержки?

- [ ] Нет или маленькая → Managed-сервисы (BigQuery, Atlas, AWS RDS) / Встраиваемые (SQLite, DuckDB)

- [ ] Да, есть → Self-hosted (PostgreSQL, Cassandra, ClickHouse, MongoDB)

## 10. Надо ли париться о безопасности?

- [ ] Уровни доступа, роли, аудит → Реляционные (PostgreSQL, MySQL) / Документные (MongoDB Enterprise)

- [ ] Шифрование данных (на rest и in transit) → PostgreSQL, MongoDB, Cassandra, коммерческие версии

- [ ] Регуляторные требования (GDPR, HIPAA, PCI DSS) → PostgreSQL, Managed-сервисы (AWS RDS, Azure)

## 11. Есть ли бюджет на оплату?

- [ ] Нет → Open Source (MySQL, PostgreSQL, MongoDB Community, Redis, ClickHouse) с учётом лицензий (SSPL для MongoDB)

- [ ] Да → Коммерческие БД (SQL Server) / Managed-сервисы (BigQuery, Atlas, Amazon RDS) / Коммерческие версии OSS (MongoDB Enterprise)

## 12. Что ещё стоит учесть?

- [ ] Сообщество и документация → PostgreSQL, MySQL, MongoDB (большое сообщество); ScyllaDB, JanusGraph (меньше поддержки)

- [ ] Интеграция с DevOps → Поддержка CI/CD, Docker, Kubernetes (PostgreSQL, MongoDB, ClickHouse)

- [ ] Нужно ли тестирование (?) → Провести прототипирование и нагрузочное тестирование перед выбором (например, PostgreSQL vs. MongoDB)

# Пример дизайна БД по алгоритму выше

**Кейс 1.** _Сеть из 5 булочных в Новосибирске разрабатывает систему для управления заказами, учёта продаж, запасов и лояльности клиентов. Данные включают заказы, товары, клиентов и транзакции. **Объём данных** небольшой (гигабайты), **команда** состоит из 1–2 разработчиков, **бюджет** ограничен, но требуется надёжность для финансовых операций. Система будет работать локально, без облака._

## Алгоритм выбора:

1. **Какие задачи будет решать проект?**
   Учёт заказов, продаж, складов, программа лояльности → Реляционные (PostgreSQL, MySQL).

2. **Что за данные?**
   Структурированные (таблицы с заказами, товарами, клиентами) → Реляционные (PostgreSQL, MySQL).

3. **Какой объём?**
   Гигабайты → Реляционные (PostgreSQL, MySQL) / Встраиваемые (SQLite для низкой нагрузки).

4. **Какой режим работы?**
   Транзакции (деньги, заказы) → Реляционные с ACID (PostgreSQL, MySQL).
   Частое чтение (каталог товаров, справочники) → Реляционные (PostgreSQL, MySQL).

5. **Какая скорость доступа нужна?**
   Высокая скорость отклика (клиенты ждут при оформлении заказов) → Реляционные с индексами (PostgreSQL).

6. **Нужен ли сложный поиск?**
   По точным значениям (поиск по заказам, товарам) → Реляционные (SQL WHERE в PostgreSQL).

7. **Как база справится с ростом данных?**
   Вертикальное масштабирование (для 5 булочных достаточно одного сервера) → Реляционные (PostgreSQL).

## Пример 1 (продолжение)

**8. Есть ли возможность использовать облачные сервисы?**
Локальные сервера → PostgreSQL, MySQL.

**9. Есть ли команда для поддержки?**
Маленькая команда → Встраиваемые (SQLite) или Managed-сервисы, но для локального сервера лучше PostgreSQL (простота настройки).

**10. Надо ли безопасность?**
Уровни доступа, роли, аудит (для финансовых данных) → Реляционные (PostgreSQL).
Регуляторные требования (учёт транзакций) → PostgreSQL.

**11. Есть ли бюджет на оплату?**
Ограниченный → Open Source (PostgreSQL, MySQL).

**12. Что ещё стоит учесть?**
Сообщество и документация → PostgreSQL (большое сообщество, множество туториалов).
Интеграция с DevOps → PostgreSQL (поддержка Docker).
Тестирование → Протестировать PostgreSQL vs. MySQL для производительности на локальном сервере.

**Выбор:** _PostgreSQ** — реляционная база с поддержкой ACID-транзакций, надёжная для финансовых операций, простая в настройке, с большим сообществом и бесплатной open-source лицензией. SQLite может быть рассмотрена для прототипа, но для надёжности транзакций лучше PostgreSQL._

## Пример 2

**Кейс.** _Стартап разрабатывает мобильное приложение для доставки лекарств, питания и средств ухода для диабетиков. Включает персонального ИИ-ассистента, который даёт рекомендации по питанию, активности и лекарствам на основе данных с фитнес-браслетов._
**Данные:** профили пользователей, заказы, временные ряды с браслетов (пульс, уровень сахара), рекомендации. Ожидается рост пользователей, команда небольшая (2–3 разработчика), бюджет ограничен, предпочтение облачным сервисам.

### Алгоритм выбора:

**1. Какие задачи будет решать проект?**
Мобильное приложение + ИИ-ассистент → Встраиваемые (SQLite для оффлайн) + Бэкенд (PostgreSQL, MongoDB) + Векторные (Qdrant, pgvector) для рекомендаций.

**2. Что за данные?**
Структурированные (пользователи, заказы) → Реляционные (PostgreSQL).
Временные ряды (данные с браслетов) → Time-Series (TimescaleDB, InfluxDB).
Текст и эмбеддинги для рекомендаций → Векторные (Qdrant, pgvector).

**3. Какой объём?**
Гигабайты на старте, потенциально терабайты → Реляционные (PostgreSQL) / Time-Series (TimescaleDB) / Векторные (pgvector).

**4. Какой режим работы?**
Транзакции (заказы, оплаты) → Реляционные с ACID (PostgreSQL).
Частые записи (данные с браслетов) → Time-Series (TimescaleDB).

**5. Какая скорость доступа нужна?**
Высокая скорость отклика (пользователь ждёт рекомендаций и заказов) → Реляционные (PostgreSQL) / Векторные с индексами (pgvector).
Кэш для сессий → Ключ-значение (Redis).

**6. Нужен ли сложный поиск?**
По смыслу (рекомендации по питанию, активности) → Векторные (Qdrant, pgvector).
По точным значениям (заказы, пользователи) → Реляционные (PostgreSQL).

**7. Как база справится с ростом данных?**
Горизонтальное масштабирование (рост пользователей) → Распределённый SQL (YugabyteDB) или NoSQL (MongoDB).
Геораспределённость (для пользователей в разных регионах) → YugabyteDB, DynamoDB.

**8. Есть ли возможность использовать облачные сервисы?**
Облако → Amazon RDS, Google Cloud SQL, Atlas (MongoDB), Timescale Cloud.

**9. Есть ли команда для поддержки?**
Маленькая команда → Managed-сервисы (AWS RDS, Timescale Cloud, Atlas) / Встраиваемые (SQLite для мобильного оффлайн).

**10. Надо ли безопасность?**
Уровни доступа, роли, аудит → PostgreSQL, MongoDB Enterprise.
Регуляторные требования (GDPR, HIPAA для медицинских данных) → PostgreSQL, Managed-сервисы (AWS RDS).

**11. Есть ли бюджет на оплату?**
Ограниченный → Open Source (PostgreSQL, TimescaleDB, pgvector) с использованием managed-сервисов для упрощения.

**12. Что ещё стоит учесть?**
Сообщество и документация → PostgreSQL, TimescaleDB (большое сообщество).
Интеграция с DevOps → PostgreSQL, TimescaleDB (поддержка Docker, Kubernetes).
Тестирование → Протестировать PostgreSQL с pgvector vs. Qdrant для рекомендаций, TimescaleDB vs. InfluxDB для временных рядов.

**Выбор:** _**PostgreSQL (с pgvector)** для профилей пользователей, заказов и транзакций (ACID, надёжность, HIPAA), **TimescaleDB** для временных рядов с фитнес-браслетов (высокая скорость записи, сжатие), **Redis** для кэширования сессий и рекомендаций. **pgvector** для векторов рекомендаций ИИ-ассистента. Для упрощения — managed-сервисы (**AWS RDS для PostgreSQL, Timescale Cloud**). **SQLite** для оффлайн-режима в мобильном приложении._
